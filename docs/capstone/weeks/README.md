# Weekly planning and execution

Quinton adopted a Sunday planning routine on October8,2026. Each week has one living work plan:
`WEEK-NN-WORK-PLAN.md`. It is the daily task/specification list, not a replacement for the approved
proposal, master schedule, experiment records or component contracts.

**Current:** [Week1 work plan](WEEK-01-WORK-PLAN.md), October5–11.
**Next:** [Week2 development plan](WEEK-02-WORK-PLAN.md), October12–18; early draft for Sunday review.
**Template:** [Weekly work plan](WEEKLY-WORK-PLAN-TEMPLATE.md).
**Human time:** [Hours log](HOURS-LOG.md).

## Sunday routine

1. Review the outgoing week's completed work, experiment outcomes and remaining gates with Quinton.
2. Reconcile hours and course/Trello status; never count unattended training as human work.
3. Move unfinished tasks deliberately, with their evidence, dependency, owner and carryover reason.
4. Copy the template into the next numbered week and set its Monday–Sunday dates.
5. Choose the week's outcomes and distinguish required closeout work from optional improvements.
6. Specify each selected task: purpose, inputs, implementation scope, outputs, verification and done condition.
7. Order development around dependencies and available time; reserve long training slots for explicit questions.
8. Agree on the first task so Monday can start with implementation rather than reconstructing context.

This is a user-led planning routine. No automatic reminder or background Sunday job is configured
by these documents.

## During the week

Update the task row when starting, blocking, completing or deferring work. Add material decisions and
scope changes to the short update log. Link implementation/results instead of duplicating full reports.
Before another agent or machine takes a task, assign ownership and a separate working branch; keep
running experiment code fixed. Planning does not itself send messages to another chat.

Older dated queues and evidence maps remain historical references. When they disagree with current
facts, record a dated correction and preserve their evidence. Do not repeat completed checks solely
to refresh a checklist or mark unverified product requirements complete.
