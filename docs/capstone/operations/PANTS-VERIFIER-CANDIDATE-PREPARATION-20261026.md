# Preparing predictions for the false-positive verifier

Status: preparation plan, NOT an inference launch receipt. No candidate predictions
or verifier weights have been generated by this work. Preserve all original pins.

## What completed training establishes

The candidate generator is the fresh SuPreM segmenter trained on the prospective
800-patient partition, with the fixed terminal 24,000-update checkpoint. It is
not the verifier. Its job is to produce realistic lesion candidates on patients
excluded from its fine-tuning and checkpoint selection.

The verifier hypothesis remains **untested**, not accepted or rejected: no paired
generator-alone versus generator-plus-verifier comparison exists yet. Training
loss cannot substitute for native Dice, false alarms or small-lesion sensitivity.
Retain the design-informed/exploratory label: preprocessing margins used broader
training annotations, and SuPreM pretraining membership is not established.

## Implementation gaps found in the existing code

1. GeneratorInputs deliberately denies all reserved/development loads. Keep that
   class unchanged; implement a separate inference-only provider bound to the
   actual frozen partition and checkpoint, with no optimizer interface.
2. Existing predict_native reconstructs probabilities but returns only hard codes
   and geometry diagnostics. Candidate probabilities require an additive exporter
   proven to reproduce the existing hard-code result, including ties, native
   orientation, outside-region background and complete tile coverage. Do not
   substitute a different lesion threshold or silently change numeric precision.
3. Existing candidate_verifier_v1.validate_provenance supports only fit/calibration,
   not the now-frozen tuning role. Add a separately versioned three-role contract;
   do not rename tune as fit or weaken the old function. Bind generator exposure
   to the verified training history, not a caller-supplied assertion alone.
4. No real candidate archive or measured size/resource distribution exists yet.
   Network architecture and patch representation remain undecided. Do not assume
   all candidates fit a fixed crop or that candidates equal independent patients.

## Ordered work and acceptance gates

1. **CPU engineering:** separate provider, immutable candidate manifest and export
   contract; synthetic tests for role refusal, coordinate alignment, padding,
   orientation, ties, disconnected components, zero-candidate cases, and exact
   baseline reconstruction. Score threshold zero must recover the entire baseline.
2. **Freeze a bounded pilot request:** preselect fit-role cases using existing
   metadata (annotation-negative and small/medium/large positive strata); no new
   duplicate/coverage audit. Include difficult existing cases where applicable.
   Case IDs and order, exact checkpoint/code/config hashes, GPU/RSS/time/storage
   caps and failure behavior must be recorded BEFORE dispatch. Suggested initial
   resource ceiling: six cases, 60 minutes total, 12 GiB owned RSS, 6 GiB GPU and
   2 GiB new outputs, subject to metadata feasibility. These are proposed limits,
   not an authorized or measured inference budget. No automatic retry.
3. **Pilot inference and review:** complete all tiles, finite probabilities,
   identical hard predictions, aligned source geometry, zero reconstruction gaps;
   save and actually inspect overlays. Separate prediction generation from
   annotation-based labels. Account for every case, including zero candidates and
   missed lesions. Report time/tiles/storage and peak memory, not just average.
4. **Resource review:** use measured pilot costs and existing tile metadata to
   estimate full533 cost and storage, including independent backups. Obtain
   explicit bounded full-stage authority; never silently run all533 from a pilot.
5. **Role-separated archive:** retain predictions/provenance for every reserved
   patient, but expose fit labels only for initial representation design. Tuning
   selects the verifier checkpoint; calibration remains locked until that model
   and selection policy are frozen. A complete archive is not permission to inspect
   calibration outcomes early. No development results guide these choices.
6. **Verifier design and qualification:** use fit-only candidate dimensions/errors
   to select complete-component-plus-context representation and patient-balanced
   fitting. Qualify actual optimizer updates, independent backup and cold restore;
   freeze a new scientific receipt and request launch approval separately.

Keep 26-connected predicted components, no minimum-size deletion and no truth-
created proposals. Ground truth supplies candidate labels and missed-component
accounting only. Any-overlap positive labels are conservative; merged components
may overlap multiple lesions and must not be reported as one-to-one matches.
Whole-component gating cannot fix an oversized boundary of a retained component
or recover a lesion that the generator never proposed.

## Scientific decision remains unchanged

Compare the SAME frozen generator alone versus plus verifier. Primary H0: no
reduction in negative-patient alarm fraction. Require paired bootstrap95% lower
bound above zero and at least0.10 absolute reduction, plus no additional missed
positive patient, no reduction in <1mL component recall, positive native Dice
delta>=-0.01 and no increase in empty-case predicted voxel burden. Nonestimable
groups are not passes. No test-set access or clinical-safety claim.

The current 70-case development cohort is held aside from this preparation.
If a generator Dice benchmark is later desired, specify it as a frozen-checkpoint
evaluation; it must not be used to select a different generator checkpoint or
retune the verifier. This work does not initiate that evaluation.
