# Offline production adapter registry and run summaries

October27: the existing saved-package and case/literature CPU adapters now validate
their stage contracts and emit the approved `run-manifest.schema.json` v1 format.
That approved schema is unchanged. This is bounded W04-01 alignment, not complete
G3 qualification or a new training launcher.

## Shipped behavior

`offline-stage-registry-v1.json` and its strict schema declare the two workflows'
stage/dependency/input names, output members, owning validators, resource class,
locks, capacity policy, cancellation/recovery limits and environment requirements.
There is no dynamic command execution from registry strings. Only the existing
registered Python adapter callbacks are passed by the two CLI entry points.
Unknown workflows, extra stages, changed dependencies/input declarations or
undeclared configuration fail before run creation. Owning validators still check
output meaning; inventory checks do not replace them.

`workflow_contracts_v1.py` records invocation context before execution and verifies
terminal outputs before publishing a summary. New sidecars are under
`<workflow-root>/contracts/<run-uuid>/`:

- `context.json`: actual invocation time, Git identity/dirty flag and environment/config pins.
- `environment.json`: installed Python distribution names/versions. Literature's existing
  input pins separately identify Node and the JavaScript validator.
- `resolved-config.json`: exact plan, registry, workflow, storage reserve and sensitivity.
- `run-manifest.json`: schema-validated summary with workflow-root-relative references.

The manifest references the original request (which retains source pins and dependency
declarations), validated stage receipts and the exact resolved configuration. It does not
invent local source URIs or stage timings. Created time is invocation time; updated time
is summary observation time. Optional stage durations/completion times are omitted.
Attempts are numbered within each invocation; resume lineage remains in the original
request. Old runs are not assigned retrospective environment/timing records.

Failed stages remain failed, with no automatic retry. If terminal summary generation
also fails, a separate `summary-unavailable.json` records that problem without masking
the original stage exception. Interrupted/nonterminal runs receive no terminal summary.
The existing executor records remain the recovery authority. Summary publication uses
an exclusive atomic link; interrupted writes leave pending files rather than a readable
partial manifest. Existing summaries are never overwritten.

## Remaining boundary

The registry covers these two offline adapters, not the whole proposed production
pipeline. It describes existing size/time limits honestly; it is not a hard memory
or wall-time supervisor for arbitrary callbacks. Training/cohort admission,
accelerator locking/cancellation/stale-owner behavior and full-cohort executor
qualification remain separate. No training stage is accepted by this registry.
Complete G3 acceptance and the independent scientific/reviewer evaluations remain open.
